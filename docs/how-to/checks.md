# Локальные проверки и pre-commit hook

Используются Python 3.12 в корневой `.venv`, Node.js 24 и зависимости из `requirements.txt` и `frontend/package-lock.json`. Порядок установки описан в [README](../../README.md#локальная-разработка).

## Полный прогон

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts/check.py
```

Последовательно выполняются pytest, `alembic check`, `pip check`, `npm test` и `npm run build`. Последняя команда включает TypeScript и production-сборку. Первая ошибка останавливает запуск с ненулевым кодом.

`alembic check` требует подготовленную БД, выбранную через `DATABASE_URL` или существующую конфигурацию приложения. Checker не применяет миграции и не меняет схему автоматически. Для новой или версионированной локальной БД сначала применяют существующие миграции; для старой базы без ревизии используют [процедуру подключения](migrate-sqlite.md).

На POSIX команда имеет вид `.venv/bin/python scripts/check.py`. Путь к скрипту можно передать абсолютный из другого каталога: команды всё равно выполняются относительно корня репозитория или `frontend/`.

## Браузерная приёмка

После установки браузера из каталога `frontend` командой `npx.cmd playwright install chromium`:

```powershell
.\.venv\Scripts\python.exe scripts/check.py --e2e
```

После базового набора запускается `npm run test:e2e`. Playwright сам поднимает тестовые FastAPI и Vite; живой Gemini не вызывается. Настройки портов, подмена модели и выбор Edge описаны в [руководстве фронтенда](../../frontend/README.md#браузерная-приёмка).

## Установка локального hook

```powershell
.\.venv\Scripts\python.exe scripts/install_hooks.py
```

Установщик создаёт исполняемый `.git/hooks/pre-commit` с окончаниями строк LF. Git Bash на Windows использует `./.venv/Scripts/python.exe`, POSIX — `./.venv/bin/python`. Hook запускает `scripts/check.py --staged` и блокирует коммит при ошибке проверки.

Идентичная повторная установка безопасна. Если уже существует другой pre-commit или настроен `core.hooksPath`, установщик останавливается без перезаписи пользовательских файлов. Автоматической установки сторонних пакетов и изменения глобального Git-конфига нет. Каждый клон устанавливает hook отдельно.

## Выбор staged-проверок

| Изменения в индексе | Проверки |
| --- | --- |
| Пустой индекс, только `*.md` и/или `docs/` | Быстрый успешный выход |
| `src/`, `tests/`, `migrations/`, `scripts/`, корневые `requirements*.txt` | pytest и `alembic check` |
| `constraints.txt`, `pytest.ini`, `alembic.ini` | pytest и `alembic check` |
| `frontend/`, кроме документации | `npx tsc -b` и `npm test` |
| Backend и frontend вместе | Оба соответствующих наборов |
| Сам `scripts/check.py` или неклассифицированный файл | Полный базовый набор |

Переименования учитываются как старый и новый путь, чтобы перенос backend-файла в документацию не пропустил проверку удаления кода. Имена с пробелами читаются из Git без разбиения по строкам.

Выбор проверок основан на индексе, но команды читают рабочую копию. При частичном staging зелёный hook не доказывает работоспособность отдельного снимка индекса: перед коммитом нужен self-review обоих diff. Hook также не заменяет полный relevant suite по глобальному инженерному протоколу.

GitHub Actions сохраняет три независимых job, описанных в [инструкции CI](ci.md). Локальный checker не публикует ветки, не запускает удалённые workflow и не заменяет проверку первого серверного прогона.
