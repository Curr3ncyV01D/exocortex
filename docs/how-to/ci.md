# Автоматические проверки в GitHub Actions

[Workflow CI](../../.github/workflows/ci.yml) запускается при push и pull request. Также предусмотрен ручной запуск через `workflow_dispatch`. Первый серверный прогон станет доступен после публикации коммита с workflow на GitHub; кнопка ручного запуска доступна после включения workflow в основную ветку.

## Что проверяется

Три независимых job выполняются на Ubuntu 24.04:

| Проверка | Окружение | Команды и результат |
| --- | --- | --- |
| Backend | Python 3.12 | Установка из `requirements.txt` с `constraints.txt`, `pip check`, весь pytest suite |
| Frontend | Node.js 24 | `npm ci`, тесты Vitest, проверка TypeScript и сборка через `npm run build` |
| Browser E2E | Python 3.12, Node.js 24, Chromium | Отдельная `.venv`, установка браузера с системными зависимостями, Playwright с одним worker и без retries |

Браузерные тесты поднимают FastAPI из `tests/e2e_app.py` с SQLite в памяти и подменой Gemini, а также отдельный Vite. Они не используют рабочую базу и не отправляют запросы в Gemini. Ключ API и другие GitHub Secrets для базового CI не требуются; `GEMINI_API_KEY` явно оставлен пустым.

Настройки и сценарии локальной приёмки описаны в [руководстве фронтенда](../../frontend/README.md#браузерная-приёмка). Миграции SQLite входят в существующие тесты бэкенда; сборка и запуск Docker Compose остаются отдельной проверкой перед выпуском.

## Как читать результаты

Открой вкладку **Actions**, выбери запуск **CI** и соответствующий job. Обычные логи доступны для всех трёх проверок.

При сбое Backend сохраняется JUnit-отчёт `backend-failure-report`, если pytest успел создать файл. При сбое Browser E2E сохраняется `browser-failure-diagnostics`: HTML-отчёт Playwright и содержимое `test-results`, включая трассировки упавших тестов. Артефакты хранятся семь дней.

После скачивания браузерного артефакта HTML-отчёт можно открыть командой из каталога `frontend`:

```sh
npx playwright show-report /path/to/playwright-report
```

Ошибка установки зависимостей или запуска сервера может произойти до создания отчёта. В этом случае причину нужно искать в логах соответствующего шага.

## Политика запуска

- Workflow имеет только разрешение `contents: read`; авторизация checkout не сохраняется для последующих Git-команд.
- Действия закреплены по полным SHA официальных версий. Их обновления выполняются отдельными проверяемыми изменениями.
- Кэшируются загрузки pip и npm. Рабочие базы, `.env`, Python-окружение `.venv` и `node_modules` в кэш не включаются.
- Более новый запуск для того же Git ref отменяет предыдущий незавершённый запуск. Push и pull request имеют разные ref и могут проверяться отдельно.
- Job ограничены по времени: Backend и Frontend — десять минут, Browser E2E — пятнадцать минут. Автоматического повторения упавших тестов нет.
- Зелёный CI не публикует приложение или релиз. Настройка обязательных проверок перед слиянием через ruleset или branch protection выполняется отдельно.

Новые проверки графа добавляются в эти же job по мере реализации [проводника](../spec_chat_explorer.md). Деплой, публикация образов и живые проверки Gemini в базовый CI не входят.
