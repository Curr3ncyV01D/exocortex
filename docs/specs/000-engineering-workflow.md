# 000. Локальные проверки и проектный инженерный протокол

## 1. Цель и границы

**Статус:** подготовительная инфраструктура завершена; проектные инструкции сохранены на английском с согласованными уточнениями; черновик проводника требует отдельного утверждения. Основание — глобальный `~/.codex/AGENTS.md` и запрос на проектную обвязку.

**In Scope:** кросс-платформенный `scripts/check.py`, локальный pre-commit hook и его установщик без новых зависимостей, проектные инструкции `AGENTS.md`, проверка команд и атомарные коммиты инфраструктуры.

**Out of Scope:** реализация проводника, React Flow, новые миграции приложения, изменение контрактов API и бизнес-логики. Черновик `001-explorer.md` готовится отдельно после сохранения инфраструктуры и остаётся незакоммиченным до утверждения.

## 2. Ключевые решения и контракты

- Базовый режим: pytest → `alembic check` → `pip check` → `npm test` → `npm run build`. `--e2e` дополнительно запускает Playwright; `--staged` выбирает проверки по индексу Git. Любая ошибка останавливает запуск и возвращает ненулевой код.
- Используется Python корневой `.venv`, на Windows — `npm.cmd`/`npx.cmd`, на POSIX — `npm`/`npx`. Рабочий каталог вызывающего терминала не определяет пути проекта.
- Только документация (`*.md`, `docs/`) или пустой индекс: быстрый успешный выход. Backend-пути запускают pytest и Alembic; frontend-пути — `tsc -b` и Vitest. Изменение самого `scripts/check.py` и неклассифицированные файлы требуют базового режима. `constraints.txt`, `pytest.ini` и `alembic.ini` относятся к backend-проверкам.
- `alembic check` не обновляет схему. Настроенная БД должна быть подготовлена существующими миграциями; проверку подготовки инфраструктуры выполняем на отдельной временной SQLite.
- Hook записывается с LF и POSIX-путями к Python, вызывает `scripts/check.py --staged`. Чужой hook и пользовательский `core.hooksPath` не перезаписываются. Повторная установка идентичного hook безопасна.
- Глобальные стоп-правила и Git-ограничения сохраняются. Коммиты выполняются в текущей ветке; push, merge и создание веток в задачу не входят.

## 3. Веха и чек-лист

- [x] **Mode B: Smoke / Verification-First.** Реализовать проверяющий скрипт и установщик, проверить маршрутизацию режимов, ошибки и защиту существующих hooks.
- [x] **Mode B: Smoke / Verification-First.** Установить hook, прогнать базовые проверки и проверить реальный запуск через Git; сохранить инфраструктуру рабочим коммитом.
- [x] **Mode C: Consistency Check.** Актуализировать проектный `AGENTS.md`, проверить команды и ссылки, сохранить проектные инструкции отдельным коммитом.

После сохранения инфраструктуры подготовить черновик трекера проводника и остановиться для его утверждения. UI/UX и живые API в этой подготовке не меняются; ручная проверка интерфейса не требуется.

## 4. Открытые вопросы и сопутствующие находки

- Проверки `--staged` выбираются по индексу, но исполняются на рабочей копии. Hook не создаёт изолированный снимок индекса; при частичном staging нужен self-review различий `git diff` и `git diff --cached`.
- В существующих тестах миграций есть таймаут дочернего процесса 30 секунд; ранее при параллельной нагрузке наблюдался выход за него. Существующие тесты в рамках задачи не меняются.
- Первый серверный прогон уже подготовленного GitHub Actions workflow по-прежнему требует публикации коммита на GitHub и не подменяется локальными проверками.
