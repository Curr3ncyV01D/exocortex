## 2. Ключевые решения и контракты

### 2.1. Переход и выбор ветки

- Одинарный клик выбирает узел и закрепляет превью. Двойной клик ЛКМ либо Enter на узле запускает переход; Enter в полях ввода не перехватывается. Скрытые сообщения доступны для перехода.
- Если узел входит в текущую ветку, она сохраняется. Иначе единственная подходящая выбирается автоматически; при нескольких открывается диалог выбора. Принадлежность определяется цепочкой parent_id, включая скрытые сообщения, и повторно проверяется сервером.
- В диалоге видны имя и статус ветки. Main первая; остальные сортируются по имени, при равенстве — по ID. Архивные ветки доступны с отметкой статуса; переход не меняет их статус или существующие правила операций. Отмена сохраняет прежний экран.
- Для узла без подходящей ветки показывается «Сообщение не входит ни в одну доступную ветку». Выделение и превью работают, ветка автоматически не создаётся.
- Пока цель загружается, прежние лента, выбранная ветка и позиция чтения сохраняются. Ветка и новое окно применяются вместе после успешного ответа. Ошибка оставляет прежний экран с повтором; новая команда перехода отменяет предыдущую. Поздние ответы другого чата/ветки/перехода игнорируются.
- После перехода цель прокручивается к центру доступной области и подсвечивается на 3 секунды. У границ истории допустимо ближайшее достижимое положение. Движение учитывает prefers-reduced-motion.
- Обычный выбор чата или ветки открывает хвост истории. Чтение отдельных веток не запоминается; черновики и положения камеры сохраняются по существующим правилам.

### 2.2. Размеры окна и прокрутка

- Обычное открытие: последние 40 сообщений. Переход к цели: до 20 предков, цель и до 20 последующих сообщений — максимум 41. При нехватке соседей дополнительные сообщения с другой стороны не добираются.
- Автоматическая догрузка по приближению к соответствующему краю: до 40 сообщений вверх или вниз; кнопки обязательной ручной догрузки не появляются. Повторный запрос того же курсора во время ожидания блокируется, ответы объединяются без дублей.
- В ленте одновременно монтируется максимум 160 карточек сообщений. При добавлении сверху освобождается далёкий нижний край, при добавлении снизу — верхний. Сохраняются ID видимой реплики и её смещение относительно области прокрутки; вытеснённый край впоследствии можно загрузить обратно.
- Ограничиваются также полные тексты сообщений в состоянии окна. Компактный граф хранится отдельно. Компонентные состояния, необходимые для сохранности несохранённого редактирования, не должны теряться при замене окна; это проверяется регрессией вместе с черновиком ввода.
- Ошибка догрузки сохраняет уже показанные данные и позицию; повтор доступен возле соответствующего края. Пустая порция обозначает достижение границы, а не ошибку. Начальный пустой чат показывает штатное пустое состояние.
- Новые сообщения при чтении прошлого не перемещают ленту: появляется «К последним сообщениям». Если пользователь уже читает хвост, новые сообщения сопровождаются обычной прокруткой к хвосту.
- Успешное явное добавление сообщения или запуск Run переводят к актуальному хвосту. Если после запуска пользователь сам ушёл читать прошлое, завершение генерации сохраняет его позицию и предлагает перейти к новым сообщениям. Неудачная операция не перемещает ленту.

### 2.3. Контракт read-only API окна

Реализован `GET /api/v1/branches/{branch_id}/timeline/window`. Старый `GET /api/v1/branches/{branch_id}/timeline` и его list[MessageResponse], параметры и значения по умолчанию сохраняются.

| Параметр | Контракт |
| --- | --- |
| `mode` | `tail` (по умолчанию), `around`, `older`, `newer` |
| `anchor_id` | Непустой ID сообщения; обязателен для around/older/newer, запрещён для tail |
| `radius` | Только around: целое 0–40, по умолчанию 20; максимум 81 сообщение с целью |
| `limit` | Только tail/older/newer: целое 1–80, по умолчанию 40; для around запрещён |

Примеры запросов:

- `/api/v1/branches/{branch_id}/timeline/window` — хвост из максимум 40 сообщений.
- `/api/v1/branches/{branch_id}/timeline/window?mode=around&anchor_id={message_id}&radius=20` — цель и соседи.
- `/api/v1/branches/{branch_id}/timeline/window?mode=older&anchor_id={older_cursor}&limit=40` — порция строго до курсора.
- `/api/v1/branches/{branch_id}/timeline/window?mode=newer&anchor_id={newer_cursor}&limit=40` — порция строго после курсора.

Around включает anchor один раз; older/newer исключают anchor. Во всех ответах сообщения идут от корня к HEAD по parent_id, а не по created_at. В окно включаются скрытые сообщения и SYSTEM_MERGE; отдельного фильтра is_active у этого endpoint нет.

DTO `TimelineWindowResponse`:

| Поле | Содержимое |
| --- | --- |
| `branch` | Существующий BranchResponse: реальная ветка и её фактический HEAD, даже скрытый |
| `messages` | MessageResponse[] только для выбранной порции |
| `has_older`, `has_newer` | Наличие сообщений за границами возвращённой непустой порции |
| `older_cursor`, `newer_cursor` | ID первого/последнего сообщения порции, если с этой стороны есть продолжение; иначе null |
| `last_active_dialogue` | `{id: str, role: user или model}` последней активной диалоговой реплики всей ветки; null, если её нет |
| `run_target` | `{expected_head_id: str, expected_question_id: str}`, если последняя активная диалоговая реплика USER; иначе null |

В пустой порции оба флага false и оба курсора null; служебное состояние реальной ветки всё равно возвращается. При присоединении older/newer фронтенд обновляет только запрошенную границу общего окна, сохраняя сведения о противоположной. После вытеснения противоположная граница снова считается доступной, её курсор — крайнее оставшееся сообщение. Курсоры — идентификаторы сообщений, не offset, даты или удостоверение неизменности ветки.

`branch`, `last_active_dialogue`, `run_target` и порция вычисляются в одном согласованном снимке чтения. Для ожидающего вопроса применяется существующее правило: скрытые реплики пропускаются, SYSTEM_MERGE не блокирует вопрос пользователя. Семантика генерации и сборка контекста LLM сохраняются.

Ответы:

- `200` — существующая ветка, включая пустую и пустую порцию на краю.
- `404` с существующей ErrorResponse — ветка не найдена либо anchor отсутствует в её цепочке (включая ID другого чата); чужое содержимое не раскрывается.
- `422` — неверный mode, отсутствующий/лишний anchor, недопустимые limit/radius либо сочетание параметров.
- `500` с существующим безопасным ответом — нарушена целостность графа (цикл, оборванная или чужая связь). Ошибки целостности не маскируются под пустую историю.

SQL/ORM и проверка принадлежности — в storage; сервис собирает результат и контролирует снимок чтения; API валидирует параметры/DTO. Storage может обходить компактные ID и связи всей цепочки, но не должен загружать полные тексты/metadata всей истории ради последующего среза в Python. Новых таблиц, миграций или библиотек для этого контракта не требуется. Python DTO, TypeScript, клиент и контрактные тесты меняются одним логическим пакетом.

### 2.4. Окно чтения и реальное состояние ветки

В Zustand отделяются подтверждённое видимое окно, ожидающий переход и служебное состояние ветки. HEAD, ожидающий вопрос и доступность повтора/перегенерации не вычисляются из последней карточки ограниченного окна. Они определяются серверным состоянием всей ветки; клиент передаёт существующие expected_head_id/expected_question_id и сохраняет обработку конфликтов без молчаливой подмены вопроса.

Для фонового обновления служебного состояния допустим запрос window в режиме tail с limit=1: его порция не заменяет видимую ленту. На обычном открытии клиент получает tail=40 и больше не требует полного timeline для отображения. Наличие поля run_target само по себе не снимает существующие блокировки занятой ветки, ошибки 413 или ограничения повторного запуска.

Команды отправки относятся к настоящему продолжению выбранной ветки. Для ответа от старой точки пользователь явно создаёт ветку существующим действием. Положение окна не меняет маски, контекст Gemini, снимок запущенной генерации или ветку, в которой она завершится.

### 2.5. Обновление графа и ленты

- Открытый граф обновляется в фоне после успешного создания реплики/ответа, ветвления, редактирования, изменения маски, перегенерации и слияния. Близкие события можно объединять; ручная кнопка обновления сохраняется.
- Пока запрос выполняется, предыдущий граф остаётся видимым. Ошибка даёт небольшое сообщение с повтором; камера сохраняется. Выделенный ID сохраняется, пока узел существует. После смены чата прежние данные не отображаются в новом чате.
- Автообновление запускается успешными операциями этого клиента; серверные push-уведомления, polling, SSE и WebSocket в эту веху не добавляются.
- Закрытый Проводник не запрашивает граф; при открытии получает свежие данные. Обычная прокрутка ленты и обновление графа камеру не перемещают.
- Видимые изменённые сообщения обновляются по ID, изменения вне окна не заставляют загружать всю историю. Служебное состояние ветки актуализируется отдельно. Новые реплики за пределами окна обозначаются возможностью вернуться к хвосту.
- Запоздалые ответы чтения, начатые до смены чата/ветки/цели или успешной мутации, не перезаписывают более новые данные. Запросы имеют проверяемую актуальность и отмену; окно, границы пагинации и метаданные применяются согласованно.

## 4. Открытые вопросы и сопутствующие находки

- Дополнительные UX-сценарии согласованы пользователем: ошибки сохраняют экран; обычный выбор открывает хвост; диалог показывает статусы веток; явная отправка переводит к хвосту; граф обновляется в фоне. Параметры и DTO реализованы и проверены контрактными тестами.
- Обязательные риски регрессии: подмена настоящего HEAD/цели Run концом видимого окна; потеря редактора при вытеснении; применение ответа, начатого до мутации; нарушение позиции при изменении высоты Markdown. Они покрываются тестами внутри соответствующих этапов.
- Ограничение DOM в 160 карточек не ограничивает контекст LLM и не означает лимит токенов отдельного сообщения. Большие Markdown-сообщения остаются отдельным фактором производительности; новая библиотека виртуализации не включается автоматически.
- Автотесты используют подмену Gemini. Удалённый CI не считается пройденным до реального запуска; push и merge требуют отдельного указания. Документация фактического поведения обновляется после реализации, запланированный API заранее не объявляется существующим.
- Если при Contract-First RED выявится противоречие с существующим контрактом или понадобится архитектурное расширение, остановиться и согласовать его. Уже существующие проверки не ослабляются во время GREEN/REFACTOR.

При подготовке frontend RED HTTP-фикстуры переведены на утверждённый контракт, проверка отсутствия HTTP-догрузки заменена проверкой двух курсорных запросов с сохранением проверок количества карточек и позиции.
- В GREEN обнаружены пропущенные расширения `.js` в helper-импортах E2E. Исправление путей и транзитивного type-only импорта разрешено пользователем; утверждения не изменены.
- Регрессионный тест восстановления потерянного HTTP-ответа подтвердил отсутствие уведомления графа. Подтверждённое серверным чтением изменение HEAD теперь уведомляет граф; тест прошёл.
- Первый [PR CI](https://github.com/Curr3ncyV01D/exocortex/actions/runs/45648184851) завершился с Browser E2E 13/14: MVP-сценарий превысил 45 секунд. Трассировка показала ввод в поле предыдущего чата до завершения создания нового. По разрешению пользователя добавлены ожидания заголовка нового чата и закрытия диалога, без изменения прикладного кода, прежних assertions и таймаута. Исправление сохранено в `23ff5b3`; повторный CI прошёл.

### Сохраняющиеся ограничения

- Vite предупреждает о директиве `use no memo` в зависимости `react-compiler-runtime`; сборка проходит, предупреждение не подавлялось.
- Ограничение числа карточек не устраняет стоимость рендеринга отдельного очень большого Markdown-сообщения. Дополнительная виртуализация и функции из Out of Scope остаются будущими задачами.
